# Platypus 2.9 — Map and territory · Surprise and causes · Workshop book

Development plan to carry out step by step, one task at a time. It lives in the repository at `docs/plans/2.9-map-and-territory.md`.
Each task has a checkbox: `[ ]` to do, `[~]` in progress, `[x]` done, `[!]` blocked (with the reason below it).
At the bottom is the **Journal**, where whoever works on the plan records, at every step, what they did, what they verified and the decisions they made. The Journal is written in English.

## The idea in one line

Platypus can't look inside the model's head, but it sees both the agent's **map** (what it has read, said and done) and the **territory** (the disk, the outcomes of commands). This version measures the distance between the two.

There are three features:

1. **Map versus territory**: stale memories, invented paths, ungrounded claims.
2. **Surprise seismograph**: when the world proves the agent wrong; whether it corrects itself or insists; whether it really goes to the cause.
3. **Workshop book**: the project's history, told in the office by **Grandpa** and, only with the user's permission, passed on to the agent through `CLAUDE.md`.

## Project rules, to follow in every task

- **Engine without dependencies:** `src/core` uses only Node.js modules. Don't add npm packages.
- **Visible strings:** always through `tr('Italian text', {placeholders})` or `trn(singular, plural, n)`, never `t()`, which is the time variable. The key of every string is the Italian text: the labels in this plan are given in English, so the code uses their Italian equivalent as the key and the English text as the translation. After every change to strings: `npm run i18n:check`, then fill in `src/i18n/locales/en/*.json`, with a new `grounding.json` file for this version.
- **Cross-platform:** paths with `path`/`posix` and no shell commands specific to one system. Everything must work on Windows, macOS and Linux.
- **Privacy:** everything stays local, no network calls. The Workshop book lives in `~/.platypus/bottega/` (use `dataDir()` from `src/paths.js`).
- **Slow or risky features are lazy and guarded:**
  - disk checks (`fs.statSync`) only when the view is opened or at most every 10 s per session, with a cache;
  - nothing blocks the interface;
  - every analysis inside `try/catch`: an analysis error must never break the office.
- **Honesty in the interface:** every indicator says what it is derived from ("rebuilt from what the agent does, not from what it thinks"). Uncertain verdicts are shown as such, for example "can't tell" or "likely".
- **Demo:** every feature must be visible in the demo (`src/core/demo.js`, `src/core/demoworld.js`), with at least one scenario built on purpose.
- **Tests:** every task ends with `npm test` green. New parsers have dedicated tests in `scripts/smoke-test.js`, or in `scripts/unit-test.js` called by `npm test`.
- **Commits:** one per task, message in English in the imperative mood, with the attribution lines you usually use. **Never push** unless the user asks.

## A. Map versus territory

### A1 · Stale memories  [x]

A file the agent read has since changed on disk, but the agent hasn't read it again.

- **Last contact.** In `AgentWorld.touch` and `end`, record for each place `lastSync`: the last moment the agent saw its up-to-date content. A successful read counts, or a successful edit of its own, which aligns its map with what it wrote. The outcome is what counts, not the start of the action.
- **Disk check.** New module `src/core/grounding.js` with `checkStale(session, agentWorlds, cwd)`:
  - for places that are project files and have `lastSync`, call `fs.statSync` (10 s cache per session);
  - a place is **stale** if `mtime > lastSync + 1500 ms`.
- **Who changed it.** If another agent in the same session edited that file after `lastSync`: "changed by NAME". Otherwise: "changed outside the session (by you or another program)".
- **Blind edit.** If the agent edits a stale file without reading it again, record a serious `blindEdit` event. If the edit fails with Claude Code's message "has been modified since read" (or similar), mark the event as `caught` (caught in time).
- **API.** `GET /api/grounding?sid&aid[&replay]` returns `{ stale:[{key, readAt, mtime, changedBy}], ghosts:[…], claims:[…], score }`. Computed lazily, only on request.
- **Sessions that can't be read from here** (Cowork, unmounted WSL): no disk check, `stale: null` with the reason.

### A2 · Invented paths  [x]

Files the agent mentions or tries to open that don't exist.

- **Sources:**
  1. failed `Read`/`Edit` with "does not exist", "ENOENT" or "No such file";
  2. command output with "No such file or directory: X" or "cannot find X";
  3. paths mentioned in its replies (in backticks or in `folder/file.ext` form) that don't exist on disk and that no agent in the session created.
- **Reuse.** Use `relKey`, `pathsInCommand` and `EXT` from `worldmap.js`. Don't add new path parsers.
- **Marking.** On the place, `ghost: true` with `ghostAt` and the source. If the file is created later (by the agent or by others), the ghost becomes "created later": it wasn't a hallucination, it was an intention.
- **Tests:** parsers for the three sources with Italian and English examples, Windows and POSIX paths.

### A3 · Talks without touching  [x]

The claims in the agent's replies, compared with what it actually did.

- **Extraction** in `grounding.js`, `extractClaims(text)`: simple, transparent rules, in Italian and English. Each claim is `{kind, text, file?}`:

| Kind | Examples |
|---|---|
| `tests` | "i test passano", "tests pass", "all green", "suite verde" |
| `verified` | "ho verificato", "funziona", "verified", "works", "confermato" |
| `fixed` | "ho corretto X", "fixed X", "risolto" |
| `created` | "ho creato X", "added X" |
| `done` | "completato", "fatto", "done" |

- **Supporting evidence**, searched for within the same turn, that is since the user's last request or, for a subagent, since its task:
  - `tests` → a successful test command **after** the last edit to a file;
  - `verified` → a successful run or check after the last edit;
  - `fixed X` / `created X` → a successful edit to X (or to a file with that name);
  - `done` → no evidence required, but it stays "ungrounded" if the turn has a failed test not followed by a successful one.
- **Outcome:** `grounded` (with the step that proves it), `ungrounded` (no evidence), `contradicted` (the last relevant outcome is a failure).
- **Data.** Use the `reply` pieces of `AgentMind` (full text) and the `steps` of `AgentWorld`. The full text of the **latest** replies must be kept, at most 20 per agent and 8,000 characters each, in memory only.
- **Optional, if there's time left:** "telepod" effect. The ungrounded sentence is shown slightly "scrambled" (CSS glitch) with the explanation "it arrived without evidence".

### A4 · "MAP AND TERRITORY" view and signals in the office  [x]

## B. Surprise seismograph

### B1 · Surprise events  [x]

> Part 1/2 done in parallel (`classifyFailure()`, `errorExcerpt()`), part 2/2 here (the score); see the Journal.

- **Computation.** In `AgentWorld.end` (or in `grounding.js`, fed by `worldEnd`) compute for each outcome a **surprise** between 0 and 1, with a reason and an excerpt.
  - **Base by type:**

| Outcome | Surprise |
|---|---|
| failed test | 0.7 |
| failed command | 0.5 |
| missing file | 0.6 |
| permission denied | 0.4 |
| timeout | 0.6 |
| `Edit` failed because the string isn't there | 0.5 |
| syntax or compile error | 0.6 |

  - **More surprising** if the same command or signature succeeded before (+0.3: "it used to work").
  - **Less surprising** if it's the first attempt at a new command (−0.2) or if the agent had just written a test that is meant to fail (TDD, heuristic on the name of the test just edited).
  - **Excerpt:** the first meaningful line of the error (max 160 characters). Skip empty lines and noise prefixes.
- **Output classification** with a new `classifyFailure(output, cmd)`, with tests: Jest/Vitest, pytest, Go, `cargo test`, `npm ERR`, `tsc` (`file(12,5): error TS…`), Node stack trace, Python traceback, PowerShell, "command not found".

### B2 · Corrects itself or insists?  [x]

- **Reaction** to the surprise, looking at the same agent's next 3 steps:
  - `corrects`: reads something new, edits a file, changes command or arguments;
  - `insists`: repeats the same signature with no edits in between;
  - `stops`: no action, or end of the turn, or a request to the user.
- **Recovery time:** how many steps and how many seconds until the next success of the same signature or of the same verification command.
- **Summary indicator per agent:** "corrects itself X times out of Y".

### B3 · Did it understand the cause?  [x]

> Part 1/2 done in parallel (`extractErrorRefs()`), part 2/2 here (assessment and chains); see the Journal.

- **References in the error.** New `extractErrorRefs(output, cwd, shellCwd)` → `[{file, line}]`. Formats, with tests:
  - `at fn (path:line:col)` and `at path:line:col`;
  - `File "x.py", line N`;
  - `path:line:col: error`;
  - `path(line,col): error TS`;
  - Go `path.go:line`;
  - Rust `--> path:line:col`;
  - Windows paths.
- **Normalization:** as in `worldmap.js` (`relKey`, `shellCwd`). Discard `node_modules` and system files, but remember that they were discarded.
- **Assessment** of the first edits after the surprise (within 6 steps):
  - `follows the trail`: touches a cited file;
  - `looks elsewhere`: edits files that weren't cited;
  - `still thinking`: no edits;
  - `no trail`: the error doesn't cite any file, so it can't be judged.
- **Chain cause → effect → fix → confirmation:** {surprise, cited files, edit, verification}. It is **complete** when the same verification that had failed succeeds again.

### B4 · "SURPRISE AND CAUSES" view and signals in the office  [x]

- **The view.** Fourth view of the map.
  - **Seismograph**: horizontal timeline with vertical spikes as tall as the surprise, colored by reaction: green corrects, red insists, grey stops. The timeline is shared with the other views.
  - **List of causal chains**, each as a small sequence of boxes "error → cited file → edit → confirmation", with its status.
  - At the top: "corrects itself X/Y · follows the trail X/Y · complete chains X/Y".
  - With "Whole session": one seismograph per agent, one below the other.
- **In the office:** when a strong surprise arrives (≥ 0.7), a shaking "!?" briefly appears above the agent. If it insists twice, the cloud turns grey: reuse `annoyedUntil` or a new `puzzledUntil`.
- **Legend** updated.

### B5 · Demo and tests for B  [x]

- **Demo scenario:**
  - TEST-RUNNER runs `npm test`: it fails with a stack trace citing `src/auth/refresh.ts:42`;
  - it reads `refresh.ts`, edits it and runs the tests again, which pass: complete chain;
  - a second agent (the PLAN that is already drifting) gets an error citing `src/db/migrate.ts`, but edits `src/ui/components/Menu.tsx`: looks elsewhere;

## C. Workshop book and Grandpa

### C1 · Project memory  [x]

- **New module** `src/core/bottega.js`.
  - **Project key:** `sha1` of the normalized folder (lowercase on Windows, `/` as separator), plus a readable name.
  - **File:** `~/.platypus/bottega/<key>.json`, saved at intervals like `stats.js`.
- **Lessons**, each `{id, kind, key, title, detail, count, sessions:[…], first, last, evidence:[{sid, t, agent, excerpt}], weight, pinned, ignored}`.

| Kind | When |
|---|---|
| `flaky-command` | a verification command that fails often or intermittently |
| `fragile-file` | a file present in many causal chains, or edited and then followed by failures |
| `known-fix` | an error pattern (normalized excerpt, without line numbers) followed several times by a fix to the same file |
| `loop-trap` | where agents go into a loop (repeated signature with errors) |
| `stale-trap` | files that often become stale memories (several agents working on them together) |
| `ghost-path` | recurring invented paths, for example a renamed file that agents keep looking for under the old name |
| `slow-step` | commands that stay stuck for a long time |

- **Sources:** the events from A and B, live, already computed. No new reads.
- **Weight:** grows with the number of cases and of distinct sessions, and decays over time (half-life of 30 days). Lessons with a low weight and a single case stay "observations", not lessons.
- **Learning from the archive.** A `learnFromArchive(projectKey)` function that rereads the project's past transcripts with `archive.js` (`loadEvents`) and an `OfficeState` without an interface, as the replay does but at full speed. It sits behind a "Learn from the archive" button and runs in the background, in chunks, without blocking the server.
- **API:**
  - `GET /api/bottega?cwd|sid` → the project's lessons;
  - `POST /api/bottega` with `{action: pin|ignore|unignore|forget, id}`;
  - `POST /api/bottega/learn`.

### C2 · Grandpa in the office  [~]

- **New NPC** in `game.js`, next to the cat, the annoying coworker and the janitor: **Grandpa**, an old man with white hair (reuse the "old-timer" age style), a cardigan and the book under his arm.
- **When he shows up.** When an agent's current action **matches** a lesson with a high weight:
  - it is about to run a `flaky-command`;
  - it edits a `fragile-file`;
  - it gets an error that matches a `known-fix`;
  - it looks for a known `ghost-path`.
- **What he does.** He walks up to the desk and says the lesson in the balloon, in a human, short way, for example "Last time this e2e got stuck three times (12 and 18 October)" or "EXPLORE already fixed that error in refresh.ts".
- **Limits.** At most one appearance every 3 minutes per floor. Never on the same agent twice in a row for the same lesson. Can be turned off in the options (`elderEnabled`).
- **Learning switch** (Max's decision, 2026-10-23): next to `elderEnabled`, a second option `bottegaLearn` (on by default) turns off the book's learning, both live and from the archive.
- **Clicking Grandpa:** opens the Book on that lesson.

### C3 · The Workshop book  [ ]

- **Where it opens:** from the floor's board ("BOOK" button) and from the lobby ("WORKSHOP" tab with the projects).
- **Content:** lessons sorted by weight, each with:
  - title and detail;
  - "seen N times in M sessions, from … to …";
  - the evidence, that is session, time and excerpt. If the session is in the archive, the evidence opens the replay at that point, with `POST /api/replay` `start` + `seek`.
- **Actions:** pin, ignore, forget.
- **Honesty:** the book says clearly that the lessons are **inferred from facts** (outcomes, repetitions, fixes), not certain rules.

### C4 · Passing the tradition on to the agent (CLAUDE.md)  [ ]

> Progress: part 1/2 done in parallel — the safe writer `src/core/claudemd.js` with its tests (see the Journal). Still to do: generating the text from C1's lessons, the preview, the buttons and the API.

- **Proposed text.** "Propose for CLAUDE.md" button: generates a Markdown section, in the language set in the options, with the pinned lessons and the strongest ones, short and actionable, for example "The e2e test `npm run test:e2e` is flaky: run it once more before investigating."
- **Preview, then two choices:**
  - **Copy**, to the clipboard;
  - **Add to CLAUDE.md**: writes into the `CLAUDE.md` in the project folder, between `<!-- platypus:bottega:start -->` and `<!-- platypus:bottega:end -->`. If the section exists it replaces it, otherwise it appends it at the end. Before writing it asks for confirmation with a dialog showing the path, and saves a copy `CLAUDE.md.platypus-backup`.
- **Never automatic.** Never on Cowork sessions or folders that can't be written; in those cases only "Copy".
- **Tests:** text generation; insertion and replacement between the markers on temporary files; the rest of the file stays intact byte for byte.
